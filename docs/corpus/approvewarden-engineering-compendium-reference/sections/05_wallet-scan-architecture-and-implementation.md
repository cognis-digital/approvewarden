Once the list of token contracts is established, the next step is to retrieve and parse the approval data associated with each contract.

### Smart Contract Interaction and ABI Decoding

The core mechanism of **approvewarden** for identifying dangerous token approvals is rooted in its ability to scan and analyze smart contract interactions. This process begins with the **ABI (Application Binary Interface) decoding** of transaction data, which allows the tool to interpret function calls made by a wallet to various token contracts. The ABI provides a structured format for encoding and decoding function signatures, enabling **approvewarden** to extract meaningful information from raw transaction data.

At its heart, **ABI decoding** involves parsing the encoded data from a transaction's `data` field, which contains the function call being made. The `data` field is typically structured as follows: the first 4 bytes represent the **function selector**, which uniquely identifies the function being invoked (e.g., `approve(address,uint256)` for ERC-20 tokens), and the remaining bytes contain the **calldata**—the parameters passed to the function. For example, in an `approve` call to an ERC-20 token, the calldata would include the spender address and the amount of tokens being approved.

To decode this data, **approvewarden** uses a combination of predefined ABI definitions for standard token contracts (ERC-20, ERC-721, ERC-1155) and dynamic decoding techniques to handle non-standard or custom contracts. The tool leverages libraries such as **ethers.js** and **web3.js**, which provide robust ABI decoding capabilities. These libraries map the function selector to its corresponding function signature and then parse the calldata based on the function's input parameters.

For instance, when analyzing a transaction that calls `approve(address,uint256)`, **approvewarden** first identifies the function selector (e.g., `0x095ea7b3`) and then extracts the spender address and the approval amount from the calldata. This process is critical because it enables **approvewarden** to determine which tokens have been approved for spending by a particular address, thereby identifying potential **infinite allowances** or **dangerous approvals**.

The accuracy of this decoding is further enhanced by the use of **contract metadata**, such as the **ABI definitions** stored in on-chain sources like **Etherscan**. These metadata sources provide the function signatures and parameter types for each contract, which are essential for correct decoding. In cases where a contract does not have an ABI definition (e.g., a private or custom contract), **approvewarden** employs heuristic-based decoding to infer the function structure from the transaction data.

This ABI decoding process is not limited to just identifying the `approve` function. It also extends to other relevant functions, such as `transferFrom`, `safeTransferFrom`, and `setApprovalForAll`, which are commonly used in token contracts. By decoding these interactions, **approvewarden** can build a comprehensive view of how a wallet interacts with various token contracts, including the types of approvals granted and the amounts involved.

One key challenge in ABI decoding is handling **variable-length data types**, such as `bytes` or `string`, which can vary in size. To address this, **approvewarden** uses dynamic parsing techniques that adjust based on the length of the data. For example, when decoding a `safeTransferFrom` call to an ERC-721 contract, the tool must correctly identify whether the `data` parameter is a simple `bytes4` or a longer `bytes` value, depending on the specific function signature.

Another critical aspect of ABI decoding is the ability to **map function calls to their respective contracts**. This requires **approvewarden** to cross-reference the function selector with known contract addresses. For example, if a transaction calls a function with the selector `0x095ea7b3`, the tool can determine that this corresponds to the `approve` function in an ERC-20 contract and then query the associated contract address from the blockchain. This mapping is essential for accurately identifying which token contracts are being interacted with and for verifying the correctness of the decoded data.

In addition to decoding individual transactions, **approvewarden** also performs **batch processing** of transaction data, allowing it to efficiently scan large volumes of wallet interactions. This is particularly important for wallets that have a history of multiple approvals, as it enables the tool to build a detailed timeline of token interactions and identify patterns such as repeated approvals or excessive allowance grants.

The effectiveness of ABI decoding in **approvewarden** is further enhanced by its integration with **on-chain data sources**, such as **Etherscan** and **Chainlink**, which provide metadata and contract information. These data sources allow **approvewarden** to validate decoded function calls against known contracts and ensure that the decoded parameters are accurate. For example, if a transaction calls a function with an unknown selector, **approvewarden** can use Chainlink's contract registry to identify the associated contract and retrieve its ABI definition for further analysis.

In summary, the **ABI decoding** mechanism in **approvewarden** is a foundational component of its wallet scan architecture. By accurately interpreting function calls made by a wallet, the tool can identify dangerous approvals, detect infinite allowances, and score drainer exposure. This process relies on a combination of predefined ABI definitions, dynamic decoding techniques, and integration with on-chain data sources to ensure precision and reliability. Through this mechanism, **approvewarden** is able to provide deep insights into token interactions, enabling users to mitigate risks associated with dangerous approvals in their wallets.

The **ABI decoding** process in **approvewarden** is not only essential for identifying individual function calls but also for understanding the broader context of a wallet's interactions with token contracts. This includes tracking the types of approvals granted, the amounts involved, and the contracts being interacted with. By analyzing these interactions, **approvewarden** can detect patterns that may indicate potential vulnerabilities or risks.

One such pattern is the presence of **infinite allowances**, where a token contract allows an address to spend an unlimited amount of tokens. This is typically implemented through the `approve(address,uint256)` function, where the approval amount is set to a very high value (e.g., `type(uint256).max`). **approvewarden** identifies such cases by decoding the `approve` function call and checking if the approved amount exceeds a predefined threshold. Another critical aspect of **ABI decoding** is the ability to detect **repeated approvals** or **overlapping approvals**, which can indicate a wallet's exposure to drainer attacks. This mechanism is well-documented in the ERC-20 standard (EIP-20), and it is essential for the approvewarden to correctly identify the contract address and the target spender associated with the dangerous allowance.

For ERC-721 tokens, which are non-fungible tokens (NFTs), the revoke mechanism is slightly different. Since each token is unique, the `approve` function in ERC-721 allows a spender to be granted permission to transfer a specific token. To revoke this approval, the same `approve` function must be called with a zero value or the `setApprovalForAll` function can be used to revoke all approvals for a given operator. The approvewarden must correctly identify whether the dangerous approval is a single-token approval or a universal approval (via `setApprovalForAll`) and apply the appropriate revoke method accordingly.

Similarly, for ERC-1155 tokens, which support both fungible and non-fungible tokens within a single contract, the revoke process involves identifying the specific token ID and the spender. ### Exposure Scoring and Risk Assessment Logic

Exposure scoring and risk assessment logic are integral to the functionality of the approvewarden system, enabling it to quantify the potential loss exposure associated with a wallet’s token approvals. At its core, the system evaluates the risk posed by each approval based on three primary dimensions: token type, allowance amount, and time-to-revoke. These factors are interwoven into a composite scoring model that assigns a numerical risk score to each approval, reflecting the likelihood of exploitation and the magnitude of potential loss. This scoring mechanism is not arbitrary but is grounded in concrete blockchain mechanics and empirical data derived from historical exploits.

The first dimension—token type—determines the nature of the approval and its vulnerability to misuse. ERC-20 tokens are the most common and have a well-defined standard, which includes functions like `approve()` and `transferFrom()`. These functions allow for infinite allowances, where an approved address can transfer any amount of tokens up to the specified allowance. This makes ERC-20 approvals particularly risky if not revoked. In contrast, ERC-721 and ERC-1155 tokens are non-fungible and fungible respectively, but they also support `approve()` and `transferFrom()` methods. However, their use cases often involve high-value assets or large quantities of tokens, which increases the potential impact of an unrevoked approval. For example, in the 2021 exploit of the Ronin Bridge, an ERC-20 token was approved without a time limit, allowing attackers to drain funds by transferring them through a malicious contract. This underscores the importance of evaluating the token type in risk scoring.

The second dimension—allowance amount—provides a direct measure of the potential loss associated with an unrevoked approval. The system calculates the allowance as a percentage of the total supply or balance, depending on the token’s structure. For ERC-20 tokens, this is typically the total supply, while for ERC-721 and ERC-1155 tokens, it may be based on the wallet’s holdings. A higher allowance percentage indicates greater risk. For instance, if a wallet holds 100,000 USDC and has an approval of 99,999,999, the risk score is significantly higher than if the approval is only 10,000. This dimension also accounts for the possibility of an infinite allowance, where the approved address can transfer any amount up to the maximum allowed by the token contract. The system identifies such infinite allowances by checking if the allowance value exceeds the total supply or balance, which is a common pattern in exploitable approvals.

The third dimension—time-to-revoke—assesses how quickly an approval can be revoked and thus mitigates the risk. The system calculates this based on the current block time relative to the approval timestamp. If the approval was made recently, the time-to-revoke is small, reducing the exposure. Conversely, older approvals have a longer time-to-revoke, increasing the likelihood of exploitation. This is particularly relevant for approvals that were granted without a time-based restriction, such as those in the 2021 Poly Network exploit, where an infinite allowance was approved years prior to the attack. The system uses this metric to adjust the risk score dynamically, ensuring that older, unrevoked approvals are weighted more heavily than recent ones.

These three dimensions are combined into a composite scoring model using a weighted formula. The token type is assigned a base weight, with ERC-20 approvals receiving the highest weight due to their susceptibility to infinite allowances. The allowance amount is scaled logarithmically to account for diminishing returns as the allowance approaches the total supply or balance. Time-to-revoke is inversely proportional to the risk score, with a decay function that reduces the score exponentially over time. This ensures that older approvals are penalized more heavily than newer ones, reflecting their increased exposure. The final risk score is then normalized to a scale between 0 and 100, where 0 indicates negligible risk and 100 represents maximum exposure.

The scoring logic is further refined by incorporating additional factors such as the token’s market cap, the wallet’s activity history, and the contract’s security audits. For example, a high-market-cap token with an unrevoked approval may have a higher score than a low-market-cap token with the same allowance, due to the greater potential loss. This refinement ensures that the scoring model is not only based on technical factors but also on behavioral and contextual data.
